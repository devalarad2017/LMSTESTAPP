LMS Architecture Brief (Plan-1)

Hybrid Strangler approach: modular-first in current monolith, then controlled extraction into 10-20 services for the new combined app.

Scope
LMS backend APIs
Current Stack
JDK 8, Spring Boot 2.7.1, WAR
Target
JDK 17, SB3, cloud-ready
Audience
Technical Architects

1) Executive Summary (High Level)

  • Current LMS is a large monolith with broad controller and service surface, deep database coupling, and many integration points.
  • Business goal is to expose full LMS capability to a new app via clean APIs while improving scalability, modularity, and maintainability.
  • Recommended path is Hybrid Strangler: first modularize the monolith by domain boundaries, then extract stable modules as independent services.
  • This avoids risky big-bang rewrites and enables continuous delivery with measurable modernization checkpoints.

2) Current Design (AS-IS) Snapshot

System Characteristics

  • Single deployable WAR; broad API base path and mixed business domains in one runtime.
  • Dual database model (Postgres + Oracle) with service-level orchestration of cross-source data.
  • Large service classes and query builders indicate migration from procedure-centric logic.
  • Multiple external integrations are executed in request path for key workflows.

Primary Risks

  • Change blast radius is high because all modules release together.
  • Performance and resilience depend on synchronized downstream behavior.
  • Domain overlap creates duplicate endpoints and similar logic in multiple places.
  • Technology baseline (JDK 8 / SB2) limits long-term platform evolution.

3) Plan-1 Target: Hybrid Strangler (Modular-First then Extract)

Recommended modernization pattern

flowchart TB A[Current LMS Monolith] --> B[Step 1: Modularize by Domain\n(inside same codebase)] B --> C[Step 2: Stabilize APIs + Contracts\n(versioning + canonical DTOs)] C --> D[Step 3: Extract Services Iteratively\nvia API Gateway routing] D --> E[Target: 10-20 Services\nindependent deploy/scale]

Why this plan

  • Preserves business continuity while reducing technical risk.
  • Creates clear boundaries before extraction (prevents distributed monolith).
  • Supports progressive rollout and rollback per domain.
  • Enables parallel delivery for product and platform teams.

4) Modular-First Domain Model (Inside Current Monolith)

Suggested domain modules

  • Lead Core (create/update/view/disposition)
  • IB Channel
  • Agency & SAM
  • Inhouse & Partner Intake
  • Renewal & Retention
  • Medical & Recruitment
  • Reports & DSR/PSF
  • Master Data
  • Identity / Access / Audit
  • External Integration Gateway

Immediate structure outcomes

  • Controllers/services/repositories grouped by domain package.
  • Shared contracts minimized; anti-corruption interfaces introduced.
  • Domain-level test suites and API contracts created.
  • Operational metrics reported per domain slice.

5) High-Level Extraction Sequence (Service Waves)

Wave 1 (Low risk): Master Data, Integration Gateway, Notification, File/Asset.
Wave 2: IAM/Audit and Bulk Upload processing.
Wave 3 (Core): Lead Core service (system of record).
Wave 4: Channel intake services (IB, Agency, Inhouse).
Wave 5: Renewal/Retention, Medical/Recruitment, Reporting slices.
Principle: extract domains with clear ownership first, then high-coupling workflows after contracts and events are stable.

6) Target Architecture Options (Short Comparison)

Option A: Modular Monolith (target)

  • Fastest stabilization, lower operations overhead.
  • Good for strong domain governance and medium scale.
  • Limitation: independent scaling/deploy still constrained.

Option B: Full Microservices (target)

  • Best independent scaling and release autonomy.
  • Highest operational complexity and migration risk.
  • Requires mature platform, contracts, and observability.

Recommended: staged hybrid

  • Start as modular monolith internally, then extract high-value modules incrementally.
  • Achieves microservice benefits without big-bang disruption.

7) Technology Direction (High Level)

  • Platform baseline: JDK 17 + Spring Boot 3.x compatibility path.
  • Edge and control plane: API Gateway, centralized authN/authZ, request tracing.
  • Resilience: retries/circuit breakers/timeouts per integration profile.
  • Observability: logs, metrics, traces as mandatory non-functional baseline.
  • Data strategy: domain ownership, read models for legacy Oracle dependencies.

8) Expected Outcomes

  • Clean API exposure to new app with lower coupling and clearer contracts.
  • Independent scaling for high-load modules and partner-facing integrations.
  • Reduced regression risk through domain boundaries and phased extraction.
  • Faster developer onboarding and easier maintenance with modular ownership.
  • Progressive path from legacy runtime to modern platform standards.
